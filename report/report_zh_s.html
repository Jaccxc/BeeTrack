Project 1：即時多目標偵測與追蹤
期末發表：2026 年 12 月 24 日

摘要

BeeTrack 是一套影片分析系統：偵測蜂巢口的每一隻蜜蜂、讓每隻蜜蜂維持同一個 ID、畫出軌跡，並計算進巢與出巢的數量。偵測器是在 BEE24 資料集上微調的 YOLO11-s。追蹤器 BeeTracker 以 ByteTrack 為基礎，對飛得快或剛跟丟幾格的蜜蜂，會在比較大的範圍內尋找。所有參數只在驗證資料上調整，官方的 5 支測試影片每個設定只跑一次。在相同偵測結果下，與預設 ByteTrack 相比，BeeTracker 把測試集 HOTA 由 40.2 提升到 45.2、IDF1 由 48.1 提升到 55.7、MOTA 由 15.0 提升到 46.7，ID 換錯由 2,186 次降到 1,314 次。若 ByteTrack 也使用相同的開新軌跡門檻，兩者 HOTA 相同（45.2）；此時我們的優勢在 MOTA（+3.5）、ID 換錯（−5%）與計數。以巢口區域取代畫面中線來計數，使我們的計數誤差由 83% 降到 35%。即使使用真值框仍有 29%，可見剩下的誤差來自擁擠巢口的軌跡斷裂，而不是偵測。系統在筆電 GPU 上離線約 54 FPS，即時 demo 為 66 FPS。

關鍵詞：多目標追蹤、蜜蜂監測、YOLO11、ByteTrack、緩衝 IoU、HOTA、巢口計數

緒論與問題定義

研究動機。出巢與回巢的蜜蜂數量會很快反映天氣、蜜源、農藥與疾病的變化。在巢口架一台攝影機並不貴，但短短幾分鐘的影片就有上千次飛行，人工計數既慢又不可靠。

困難之處。在 950 × 600 的畫面中，一個蜜蜂框大約只有 46 × 50 像素。數十隻蜜蜂長得一樣，外觀特徵幫助有限。蜜蜂會在幾格之內加速、轉向或降落，追蹤器預測的框常常和下一格的偵測框完全不重疊，於是軌跡跟丟，並以新的 ID 重新開始。巢口是最擁擠的地方，也正是要計數的地方。

輸入與輸出。輸入是蜂巢口影片。系統對每一格輸出每隻蜜蜂的框與 ID、軌跡、累計進出數量與處理速度，並產生標註後的影片與所有軌跡的 CSV 檔。

目標（課程 Project 1）：微調偵測器；建立線上追蹤器並提供軌跡與計數分析；提出有理由的改進，在相同偵測結果下與 ByteTrack 比較；完成兩組對照實驗與穩健性研究；提供可重現的 demo。

本文貢獻。

  • 為 BEE24 建立無資料洩漏的切分，驗證集包含長時間的擁擠片段。
  • 運動自適應關聯：在 ByteTrack 內部做少量修改，每一項都能單獨關閉做消融。
  • 巢口區域計數規則，並以 oracle 測試說明剩下的計數誤差來自軌跡斷裂，而非偵測。
  • 穩健性研究，並誠實列出沒有幫助的嘗試。

相關研究

即時追蹤器多半採用 tracking-by-detection：先由 YOLO11 [1] 這類快速偵測器找出物體，再由追蹤器把各格的偵測串起來。我們的 baseline ByteTrack [2] 以 Kalman filter 預測每條軌跡，用框的重疊（IoU）配對，並在第二階段利用低分偵測。DanceTrack [3] 指出，為行人設計的追蹤器在目標外觀相似、運動不規則時表現會變差，蜜蜂正是這種情況。C-BIoU [4] 在計算 IoU 前先把框放大，讓快速物體仍能配對；我們採用這個想法，並讓放大的幅度隨每條軌跡的狀態改變。OC-SORT [5] 在軌跡跟丟後修正 Kalman 狀態。BEE24 [6] 與 TOPICTrack 一同發表，後者在測試集上報告 HOTA 46.6、IDF1 59.7、MOTA 66.7；它使用不同的偵測器，因此僅供參考。我們報告 MOTA [7]、IDF1 [8] 與 HOTA [9]，全部以 TrackEval [10] 計算；人工影像劣化則參考 [11] 的做法。

資料集與前處理

BEE24 [6] 有 36 支 25 fps 的蜂巢口影片，共 446,908 個框、4,559 個蜜蜂 ID，平均每格 19.0 隻（最多 52 隻）。每個框都有追蹤 ID，因此可以計算以 ID 為基礎的追蹤指標。資料集頁面未標明授權，我們只用於本課程。影片中沒有人物。

官方切分為 31 支訓練影片與 5 支測試影片。測試集從未用於訓練、模型挑選或調參。驗證集取 4 支短的訓練影片，再加上 2 支長訓練影片各自的最後 1,000 格，因為只用短影片的話，擁擠程度遠低於長的測試影片。這些尾段與訓練影格之間留有 50 格的間隔，避免幾乎相同的相鄰影格造成洩漏。

同一組模組有兩種用法。線上 demo 對任意影片逐格執行偵測與追蹤。做實驗時，偵測器對每支影片只跑一次並把框存下來，之後每一種追蹤器設定都重播完全相同的框。這樣追蹤器之間的比較完全受控，幾十種設定也能在幾分鐘內測完。

方法與演算法

偵測器

YOLO11-s 是單階段偵測器，以 COCO 預訓練，再於 BEE24 上以單一類別「bee」微調。我們分別以 640 px 與 1280 px 訓練（實驗二）。信心分數 0.05 以上的偵測都保留，因為 ByteTrack 會用到低分的框。

Baseline 追蹤器：ByteTrack

每條軌跡由等速 Kalman filter 往前預測一格。高分偵測（≥ 0.25）以 IoU 和 Hungarian 演算法與預測配對；剩下的軌跡再與低分偵測（0.1 到 0.25）配對。沒有配對到、且分數達到 new_track_thresh 的偵測會開啟新軌跡。一直沒有配對到的軌跡會以「跟丟」狀態保留 30 格，期間可以用原 ID 重新啟用。

我們報告兩個 baseline：ByteTrack 使用 Ultralytics 預設值（開新軌跡門檻 0.25）；ByteTrack-tuned 只把這個門檻改成 0.5。我們的追蹤器同樣使用 0.5，所以 ByteTrack-tuned 可以把「關聯方法的改進」與「單純調門檻」的效果分開。

BeeTracker：運動自適應關聯

我們要解決的失敗很單純：快速蜜蜂的預測框與下一格的偵測框不重疊時，IoU 為 0，任何門檻都配不上。BeeTracker 在 ByteTrack 內部做了四項修改：

  • 自適應邊界的緩衝 IoU。計算 IoU 之前，先把框的四邊向外放大。偵測框放大固定比例 b；軌跡框放大的比例 r，則隨距上次配對的格數 ℓ，以及以「框高／格」為單位的速度 v 而增加：
    r = b + g · min(ℓ, 10) + k · min(v, 1),    b = 0.1, g = 0.1, k = 0.5
    (1)
    停著不動的蜜蜂只用小範圍搜尋；飛得快或剛跟丟的蜜蜂，則在較大的範圍內搜尋。
  • 速度衰減。軌跡跟丟期間，速度每格乘上 0.8，避免看不見的蜜蜂沿著過時的速度一路飄走。
  • 提高速度雜訊。Kalman 的速度雜訊權重加倍（1/160 → 1/80），讓濾波器更快跟上突然的轉向。
  • 延長跟丟軌跡的保留時間。跟丟的軌跡保留 60 格（2.4 秒），而不是 30 格。

這些修改都不增加需要學習的參數，所以追蹤器仍然快速且容易解釋。所有數值都在驗證資料上選定。

計數

BEE24 沒有計數標註，所以計數由軌跡推得，真值與預測軌跡套用同一條規則。計數誤差是各序列「進的誤差絕對值＋出的誤差絕對值」的總和，並與真值的進出總次數一起報告。

巢口區域（主要規則）。每台攝影機我們只在第一格上手繪一個多邊形，圍住黑暗的巢門開口，繪製時不看任何標註或預測。軌跡由多邊形外開始、在多邊形內結束，算一次「進」；由內到外算一次「出」。測試集共有 341 次真值進出（進 170、出 171）。

為什麼中線規則失敗。計畫書原本是計算穿越畫面中間一條水平線（含一小段緩衝帶）的次數。穿越線計的是軌跡「中途」發生的事件，所以在線附近徘徊的蜜蜂，或在線旁發生的 ID 換錯，都會多算或少算；只是飛過巢口前方的蜜蜂也會被計入。同一份追蹤輸出（本文方法、測試集）下，中線規則的計數誤差是 83%（262 / 316），區域規則是 35%（119 / 341）。區域規則也有弱點：軌跡若在巢口內斷掉，一次進出會變成兩段都不計的半截軌跡。

實作細節

  • 軟硬體。NVIDIA RTX 4060 筆電 GPU（8 GB）；Python 3.11、PyTorch 2.11.0、Ultralytics 8.4.208、TrackEval。執行環境由 uv.lock 鎖定。
  • 訓練。COCO 權重 yolo11s.pt；上限 50 個 epoch，以驗證集做 early stopping（patience 15）；seed 0；使用 Ultralytics 預設的資料擴增。
  • 推論。FP16、信心分數 ≥ 0.05、NMS IoU 0.7；每個偵測器的偵測結果只快取一次，所有追蹤器共用。
  • 追蹤。BeeTracker 繼承 Ultralytics 的 ByteTrack 實作，只覆寫配對距離、預測步驟與 Kalman filter。
  • 程式。beetrack 套件中每個流程步驟各一個 Python 模組。每次執行都會把參數與結果寫成檔案，所以本報告的每個數字都能追溯到來源。

提出的技術改進

問題。蜜蜂在兩格之間移動超過一個框寬時，前後兩個框完全不重疊。ByteTrack 在任何門檻下都配不上，軌跡於是跟丟，下一個偵測就開了新 ID。漏偵測或框不準會讓情況更糟。

為什麼這樣改。緩衝 IoU 讓相鄰但不重疊的框重新有重疊值 [4]。固定的大邊界會把擁擠處相鄰的慢速蜜蜂也混在一起，所以邊界只對快速或跟丟的軌跡放大，因為這些軌跡的位置確實比較不確定。使用速度衰減，是因為跟丟的蜜蜂通常已經停下、降落或轉向。提高速度雜訊，是因為以體型來看，蜜蜂的加速度比行人大得多。提高開新軌跡門檻，是為了避免擁擠處的低分框開出短命的假軌跡；這只是單純的調參，所以 ByteTrack-tuned 也使用相同的值。

與計畫書的差異。計畫書原訂以穿越線計數；我們看到穿越線的計數主要被徘徊的蜜蜂左右後，改用巢口區域。另外，「依每條軌跡調整」這件事改由邊界來做，而不是調整 Kalman 雜訊，這樣每個元件都能單獨開關。

成功標準（計畫書中已訂定）：在相同測試集、相同偵測結果下，HOTA 與 IDF1 高於 ByteTrack，且 ID 換錯較少。

實驗設定

  • 公平性。所有調參只使用驗證資料。每個設定先固定下來，再在測試集上跑一次。每個實驗只改變一個因素：實驗一只換追蹤器（使用相同的偵測快取）；實驗二只改偵測器的輸入大小（追蹤器與訓練預算相同）。
  • 評估指標。偵測：precision、recall、mAP。追蹤：HOTA（兼顧偵測與關聯）、IDF1（ID 一致性）、MOTA（主要受偵測錯誤影響）與 ID 換錯次數（IDSW）。計數：區域計數誤差。速度：端到端 FPS。
  • 穩健性條件（測試集、640 px 偵測器、不重新訓練）：(1) 掉幀，每 k 格只處理 1 格（k = 2、3、5）；(2) 四種人工影像劣化：變暗（× 0.4）、過曝（× 1.6 + 20）、水平動態模糊（1 × 9）與高斯雜訊（σ = 15）；(3) 擁擠程度，比較 5 支測試影片。

解讀。提升來自緩衝 IoU 與它的自適應邊界。拿掉緩衝會少 2.2 HOTA、多 111 次 ID 換錯。改用固定邊界會少 1.8 HOTA，可見重要的是「自適應」，不只是把框放大。速度衰減與提高雜訊各只貢獻 0.2 HOTA，延長跟丟軌跡保留時間在驗證集上沒有影響。開新軌跡門檻主要影響 ID 換錯（615 → 407）。

負面結果。有幾個想法在驗證集上試過但沒有採用。在低分階段也用緩衝 IoU、對空缺做內插、過濾短軌跡，都沒有提高 HOTA。軌跡縫合（把新軌跡接到 10 格內在附近結束的舊軌跡上）在測試集上減少了 ID 換錯（1,314 → 952），但 HOTA 降到 42.2、區域誤差升到 164，因為它有時會把兩隻不同的蜜蜂接在一起。我們也在把外觀 re-identification 做進追蹤器之前先做了測試：以蜜蜂影像訓練的 ResNet-18 選對同一隻蜜蜂的比例是 74–49%，只看最近位置是 93–70%，兩者合用仍是 93–70%。外觀沒有帶來任何幫助，所以沒有加入 ReID 分支。

失敗案例。我們的方法並非處處較好：在 BEE24-36 上 ByteTrack-tuned 的 HOTA 較高（49.1 對 46.4）；在動態模糊下我們的 ID 換錯較多（1,423 對 1,317）。在蜜蜂互相接觸的地方，放大的搜尋範圍是一種風險。

實驗二：偵測器輸入大小

目的。提高輸入解析度，是否能把小蜜蜂找得夠好，進而改善追蹤與計數？代價是什麼？控制條件。相同的模型、初始權重、訓練影像、資料擴增、seed 與訓練預算；相同的追蹤器與測試集。只改輸入大小（640 對 1280 px）。

擁擠程度

難度主要取決於軌跡的進出更替，而不是擁擠程度。BEE24-13 是最擁擠的測試影片（每格 25.0 隻），但蜜蜂大多停在原地（54 條軌跡），所有追蹤器的 HOTA 都超過 66。BEE24-34 沒那麼擁擠（20.7），卻有 1,143 條軌跡；它是最難的影片（本文 42.5、ByteTrack-tuned 41.2），也是我們的追蹤器領先最多的一支。

失敗分析

  • 巢口蜂群內的 ID 換錯（圖 3 下）。互相接觸的蜜蜂彼此遮擋，一條軌跡跟丟後以新 ID 重新開始。區域規則於是看到兩段半截軌跡，這次進出就被漏掉。這就是使用真值框仍有 29% 誤差的原因。
  • 蜜蜂消失在黑暗的巢門裡。真值會一路標進巢門，偵測器卻在那裡跟丟，軌跡還沒進入區域內就結束了。
  • 快速起飛與降落。位移大到連放大後的搜尋範圍都涵蓋不了，軌跡就會斷掉。
  • 標註差異被算成 false positive（圖 3 上）。BEE24-34 的許多「false positive」其實是真的蜜蜂：真值框比我們的框鬆很多，或是畫面邊緣的蜜蜂沒有被標註。光是這支影片就佔了我們 60.8 k 個測試 false positive 中的約 51 k，這解釋了它偏低的 MOTA。

應用與展示

應用程式是 beetrack.demo。它接受影片檔或影格資料夾，逐格執行偵測器與選定的追蹤器，輸出標註後的影片與所有軌跡的 CSV 檔。畫面上顯示每隻蜜蜂的框、ID 與一秒長的尾跡，以及巢口區域、即時進出計數與處理 FPS。計數使用與評估完全相同的區域規則。

展示影片。我們沒有自行拍攝影片。Demo 使用 BEE24-36，這是 5,000 格（200 秒）的官方測試影片，從未用於訓練或調參。在這個意義上它是「未見過」的影片，但它來自同一個資料集，不能當作系統在其他地點或其他攝影機也有效的證據。在這支影片上，demo 平均 66 FPS，計數為進 40／出 22，真值為 49 / 32，與離線評估相同。

限制與未來工作

  • 單一資料集。所有結果（包括 demo）都來自 BEE24。其他攝影機、蜂箱與光線下的表現可能不同。
  • 計數受限於軌跡斷裂。即使使用真值框，區域誤差仍有 29%。更大的偵測器、縫合與短軌跡過濾都沒有解決這個問題。
  • 相對調整後 baseline 的提升有限。與 ByteTrack-tuned 相比，我們 HOTA 打平、IDF1 略低；優勢在 MOTA、ID 換錯、掉幀穩健性與區域計數。
  • 計數規則。計數由標註的軌跡與手繪的區域推得，並非真實進巢事件的標註。這套規則適合比較追蹤器，不適合產生絕對的蜂群統計。
  • 人工穩健性測試。這些劣化都是簡單的全域影像變化；真實的黃昏、雨天或晃動的陰影並非如此。

未來工作：能在蜜蜂接觸時仍維持 ID 的關聯方法（短期外觀或姿態特徵，或 OC-SORT [5] 以觀測值修正的做法）；把黑暗的巢門明確當作「已進巢」狀態；真實進巢事件的計數標註；自行拍攝蜂巢影片；以及邊緣裝置部署。

結論

BeeTrack 把蜂巢口影片轉成蜜蜂 ID、軌跡與進出計數。在相同偵測下，與預設 ByteTrack 相比，運動自適應關聯把測試 HOTA 由 40.2 提升到 45.2、IDF1 由 48.1 提升到 55.7，ID 換錯由 2,186 次降到 1,314 次。與使用相同開新軌跡門檻的 ByteTrack 相比，HOTA 打平，MOTA、ID 換錯與計數較佳。計數上最大的改善來自規則本身：以巢口區域取代中線，使我們的計數誤差由 83% 降到 35%。即使框完全正確仍有 29%，剩下的是擁擠巢口的軌跡斷裂。1280 px 偵測器提升了 HOTA（48.0）與 MOTA（60.3），但沒有改善計數。我們的追蹤器在掉幀時退化最緩和，並在所有影像劣化下維持最佳的區域計數。系統在筆電 GPU 上離線約 54 FPS、即時 66 FPS。所有調參只使用驗證資料，測試集每個設定只跑一次。

外部模型、資料集與 AI 使用聲明

  • 預訓練模型。Ultralytics YOLO11-s 的 COCO 權重（AGPL-3.0），在 BEE24 上微調。Baseline 追蹤器是 Ultralytics 的 ByteTrack 實作，我們的追蹤器繼承自它。
  • 資料集。BEE24 [6]，自作者公開頁面下載；未標明授權，因此只用於課程作業。
  • 評估程式。TrackEval [10]，未修改。
  • AI 協助。我們使用 Claude（Anthropic）協助撰寫與除錯程式、設計與執行實驗，以及撰寫與編修本報告與投影片。所有決策、程式與結果都經過組員檢查；每個數字都來自我們程式產生的檔案，每位組員都能解釋程式碼。
