摘要

蜂巢出入口的流量，也就是出巢與回巢的蜜蜂數量，能直接反映蜂群的活動力，但靠人眼計數無法長期進行。本文提出 BeeTrack：一套從蜂巢口影片中偵測每一隻蜜蜂、為每隻蜜蜂維持固定 ID、繪出軌跡，並計算進出「巢口區域」之蜜蜂數量的系統。偵測器採用 COCO 預訓練的 YOLO11-s，以 BEE24 資料集微調；追蹤器 BeeTracker 以 ByteTrack 為基礎，加入「運動自適應關聯」：緩衝 IoU 的搜尋邊界會隨軌跡速度與跟丟的影格數放大、跟丟軌跡的速度逐格衰減、提高 Kalman 速度雜訊，並延長跟丟軌跡的保留時間。所有參數只在驗證資料上調整，BEE24 官方的 5 支測試影片（10,762 格、168,230 個框）每個設定只跑一次。在相同偵測結果下，相較於預設 ByteTrack，BeeTracker 把測試集 HOTA 由 40.2 提升到 45.2、IDF1 由 48.1 提升到 55.7、MOTA 由 15.0 提升到 46.7，ID 換錯由 2,186 次降到 1,314 次。與使用相同開新軌跡門檻的 ByteTrack 相比，HOTA 相同（45.2），但 MOTA（+3.5）、ID 換錯（−5%）與計數誤差較佳。以巢口區域取代畫面中線來計數，使本方法在測試集上的相對計數誤差由 83% 降到 35%（341 次真值進出中誤差 119）；即使用真值框仍有 29%，可見剩下的誤差主要來自擁擠巢口的軌跡斷裂。1280 像素偵測器提升了 HOTA（48.0）與 MOTA（60.3），但沒有改善計數。在掉幀處理下本方法退化最緩和（每 5 格取 1 格時，比調整後的 ByteTrack 高 2.1 HOTA、ID 換錯少 37%），且在四種人工影像劣化下都維持最低的區域計數誤差。整套流程在 RTX 4060 筆電 GPU 上離線（含影像解碼）約 54 FPS，即時 demo 為 66 FPS。

關鍵詞：多目標追蹤、蜜蜂監測、YOLO11、ByteTrack、緩衝 IoU、Kalman filter、HOTA、巢口計數

緒論與問題定義

研究動機

養蜂人與授粉研究者之所以觀察蜂巢出入口，是因為外出採集的流量會很快反映天氣、蜜源、農藥與疾病的變化。在出入口架一台攝影機並不貴，難的是把影片轉成數字：短短幾分鐘的影片就包含上千次飛行，人工計數既慢又容易出錯。若能自動追蹤每一隻蜜蜂並計算進出數量，就能做到連續且客觀的監測。

問題的困難之處

多數多目標追蹤器是為行人設計的，蜜蜂比行人難追得多。在 950 × 600 的畫面中，一個蜜蜂框大約只有 46 × 50 像素；數十隻蜜蜂外觀幾乎無法區分，外觀特徵的幫助有限；而且蜜蜂會在幾格之內加速、轉向或降落。以等速 Kalman filter 預測位置、再用框的重疊來配對的追蹤器，常會遇到快速蜜蜂的預測框與下一格偵測框完全不重疊的情形，於是軌跡跟丟、以新的 ID 重新開始，甚至和旁邊的蜜蜂對調 ID。偏偏蜂巢口正是最擁擠、也正是要計數的區域。

目標、輸入與輸出

本系統對應課程的 Project 1（即時多目標偵測與追蹤）。輸入為蜂巢口影片（影片檔或影格資料夾）；輸出為每一格中每隻蜜蜂的框與追蹤 ID、每個 ID 的軌跡與方向、巢口的累計進出數量、實測處理速度、標註後的影片，以及所有軌跡的 CSV 檔。具體目標如下：

  1. 微調一個能偵測蜜蜂的深度學習偵測器（R1）；
  2. 建立線上追蹤器，在漏偵測與短暫遮擋下仍能維持 ID，並提供軌跡與計數分析（R2）；
  3. 提出有理由的關聯改進，在相同偵測結果下與 ByteTrack 比較（R3）；
  4. 完成兩組對照實驗：關聯方法與偵測器輸入大小（R4），以 HOTA、IDF1、MOTA、ID 換錯、計數誤差與 FPS 量化評估，並分析至少三種困難條件（R5）；
  5. 提供可重現、能端到端處理影片的 demo 程式（R6）。

本文貢獻

  • 為 BEE24 建立無資料洩漏的評估流程：驗證集包含長時間的擁擠片段，並修正官方標註中重複 ID 的問題，產生 TrackEval 可用的真值。
  • 提出運動自適應關聯：在 ByteTrack 內部做少量修改，每一項都能單獨關閉做消融實驗，專門處理小而快速物體的失敗模式。
  • 訂定巢口區域計數規則，真值與預測套用同一規則，對在線附近徘徊的蜜蜂遠不敏感；並以 oracle 分析證明剩下的計數誤差來自軌跡斷裂，而非偵測。
  • 在影像劣化、掉幀與擁擠程度三類條件下做穩健性研究；誠實報告沒有幫助的嘗試（主結果中的軌跡縫合、短軌跡過濾、第二階段緩衝、內插）；demo 可輸出含即時計數與 FPS 的標註影片。

相關研究

物件偵測。YOLO 系列 [1] 屬於單階段偵測器，一次前向傳遞即可密集預測所有框，是即時 tracking-by-detection 最常見的選擇。我們使用 Ultralytics 目前的版本 YOLO11 [2] 的 small 規模。RT-DETR [3] 等 Transformer 偵測器速度相近，但所需記憶體與訓練時間超出我們 8 GB 筆電 GPU 能從容負擔的範圍。

Tracking-by-detection。SORT [4] 以等速 Kalman filter [5] 預測位置，再以 IoU 為代價、用匈牙利演算法 [6] 配對。DeepSORT [7] 加入外觀重識別特徵，但目標外觀都相同時幫助不大。ByteTrack [8] 保留低信心分數的偵測框並在第二階段配對，能找回被部分遮擋的目標；它是 Ultralytics 的預設追蹤器，也是本專題的 baseline。BoT-SORT [9] 加入相機運動補償與外觀特徵，但 BEE24 的相機固定不動，兩者都派不上用場。OC-SORT [10] 在軌跡重新被觀測到時，以觀測值修正跟丟期間的 Kalman 狀態，以處理非線性運動造成的漂移。

不規則運動。DanceTrack [11] 指出：在 MOT17 [12]、MOT20 [13] 上調好的追蹤器，遇到外觀一致、運動多變的目標時表現會明顯下降，這正是蜜蜂的情況。C-BIoU [14] 在計算 IoU 前同時放大軌跡框與偵測框，讓框不重疊的快速物體仍能配對，並串接兩種緩衝大小。我們沿用緩衝 IoU 的想法，但讓緩衝大小依每條軌跡的狀態（速度與跟丟時間）決定，而不是固定的串接層級。

昆蟲追蹤。Bozek 等人 [15] 以分割網路加上時間連結，追蹤蜂巢內部密集的蜜蜂。BEE24 [16] 隨 TOPICTrack 一同發表，該方法平行進行運動與外觀關聯，作者在 BEE24 測試集上報告 HOTA 46.6、IDF1 59.7、MOTA 66.7。這些數字使用不同的偵測器與訓練流程，本文僅作為背景參考，並非對照比較。

評估指標。CLEAR MOT 指標 [17]（MOTA、ID 換錯）主要受偵測品質影響；IDF1 [18] 衡量 ID 的一致性；HOTA [19] 則同時平衡偵測（DetA）與關聯（AssA）準確度。所有指標皆以官方實作 TrackEval [20] 計算。人工影像劣化的設計參考 Hendrycks 與 Dietterich 的 common corruption 基準 [21]。

資料集與前處理

來源與標註

BEE24 [16] 共 36 支蜂巢口影片，25 fps，解析度約 950 × 600（其中一段為 810 × 430），共有 446,908 個標註框、4,559 個蜜蜂 ID，平均每格 19.0 隻（最多 52 隻）。每個框都附有 MOTChallenge 格式的追蹤 ID（frame、id、x、y、w、h），符合規範第 7B 節「追蹤指標必須有 ID 標註」的要求。資料可公開下載（2.3 GB），不需註冊；資料集頁面沒有寫明授權，因此我們只用於本課程並引用論文。影片中只有昆蟲，沒有拍到任何人。

資料切分與防止洩漏

官方切分為 31 支訓練影片與 5 支測試影片。測試集（BEE24-12、-13、-16、-34、-36；10,762 格、168,230 個框）完全不用於訓練、模型挑選或參數調整，每個最終設定只評估一次。驗證集則從訓練影片中切出，用於偵測器的 early stopping 與所有追蹤器調參（表 1）。

提案時原本規劃以「整段訓練序列」作為驗證集。實作時發現，短的訓練序列（75 到 258 格）每格蜜蜂數遠少於兩支長測試影片；後者各有 5,000 格，且包含最擁擠的片段。若驗證集沒有長而擁擠的片段，追蹤器就會被調到錯誤的情境。因此我們保留四段完整的短序列（BEE24-10、-15、-24、-28），另外再取兩支長訓練影片 BEE24-33 與 -35 的最後 1,000 格。這兩段尾端與訓練影格之間隔著 50 格不屬於任何一方的間隔，避免幾乎相同的相鄰影格跨界洩漏。prep.py 會以 assert 檢查沒有任何一格同時屬於兩個切分。

為什麼要快取偵測結果。實驗一只能改變追蹤器。偵測器只跑一次（信心分數 0.05、NMS IoU 0.7、FP16），再把一模一樣的框重播給每一種追蹤設定，就能排除偵測端每次執行的差異，讓比較完全受控；而且數十種設定的掃描在 CPU 上幾分鐘就能跑完。

方法與演算法

偵測器

YOLO11-s 是 anchor-free 的單階段偵測器，由 CSP 式骨幹、特徵金字塔頸部，以及在三個 stride（8、16、32）上分別預測類別分數與框分佈的 decoupled head 組成。輸入 640 像素時，約 46 像素的蜜蜂在 stride 8 上大約只佔 6 格，最細的偵測頭還夠用，但對較小的蜜蜂餘裕不多；輸入加倍為 1280 像素可讓解析度加倍，但計算量變成四倍，這正是實驗二要量測的取捨。偵測結果保留到信心分數 0.05，因為 ByteTrack 的第二階段刻意使用低分框。

Baseline 追蹤器：ByteTrack

每條軌跡的 Kalman 狀態為 x = (cx, cy, a, h, ċx, ċy, ȧ, ḣ)（中心、長寬比、高度及其速度），採等速狀態轉移。process noise 與量測雜訊都和框高 h 成正比，速度的標準差為 σv = wv·h，預設 wv = 1/160。每一格的處理步驟：

  1. 所有軌跡（追蹤中與跟丟中）先預測下一格的位置。
  2. 分數 ≥ 0.25 的偵測框與軌跡配對，代價為 C = 1 − IoU·s（IoU 與偵測分數 s 融合），以匈牙利演算法求解，代價 > 0.8 的配對不採用。
  3. 剩下的追蹤中軌跡再與低分框（0.1 ≤ s < 0.25）以一般 IoU 配對，代價 > 0.5 者不採用。
  4. 尚未確認的新軌跡與剩下的高分框配對；仍未配對、且 s ≥ new_track_thresh 的偵測框開新軌跡。
  5. 超過 track_buffer = 30 格（1.2 秒）沒有配對的軌跡被移除；在此之前屬於「跟丟」狀態，仍可重新啟用。

我們報告兩個版本：Ultralytics 預設值（bytetrack.yaml，開新軌跡門檻 0.25），以及 ByteTrack-tuned：只把 new_track_thresh 改為 0.5。這是本方法也使用的唯一門檻變更，因此 ByteTrack-tuned 能把「關聯修改」的效果與「門檻調整」的效果分開。

本文改進：運動自適應關聯

我們要解決的是幾何上的失敗：快速蜜蜂的預測框與下一格的偵測框沒有重疊，IoU 為 0，任何門檻都配不上。我們在 ByteTrack 內部做了四項修改（track.py 中的 BeeTracker 類別）；設計理由與逐項消融見第 9 章。

(a) 自適應邊界的緩衝 IoU。計算 IoU 之前，寬 w、高 h 的框 (x1, y1, x2, y2) 四邊各放大比例 r：

Br = (x1 − rw,  y1 − rh,  x2 + rw,  y2 + rh)

可選後處理：因果式軌跡縫合

軌跡斷裂（一隻蜜蜂被切成好幾段短軌跡）是巢口最主要的錯誤，因此我們也評估 本文＋縫合：若一條軌跡在另一條軌跡結束後 10 格內開始，且起點離該軌跡最後的中心不超過 4 個框高，就延續較舊的 ID（貪婪法，距離最近者優先）。它只需要 10 格（0.4 秒）的延遲，可以即時執行。第 11 章會看到：縫合有助於穿越線計數，卻會傷害區域計數與 HOTA，所以不納入主要設定。

計數規則

BEE24 沒有計數標註，因此計數由軌跡定義，真值與預測軌跡套用同一條規則。每種規則下，追蹤器在序列集合 S 上的計數誤差定義為

E = Σs∈S ( |Îs − Is| + |Ôs − Os| )
(4)

其中 I、O 是真值的進、出次數，Î、Ô 是預測值。E 會與該規則的真值穿越總數一起報告。

巢口區域（主要規則）。每台攝影機只在第一格上手繪一個多邊形，圍住黑暗的巢門開口並外加約一個蜂身的邊距，繪製時不看任何標註或預測（beetrack/zones.json）。一條軌跡若第一個框中心在多邊形外、最後一個中心在多邊形內，算一次「進」；由內到外算一次「出」；起點與終點在同一側的軌跡不計。真值穿越次數：驗證集 173（進 90／出 83），測試集 341。

中線＋遲滯帶（次要規則）。在 y = H/2 放一條水平線，並設 ±0.05·H 的遲滯帶（約半隻蜜蜂，事先固定、不調整）：只有中心離開遲滯帶時，軌跡所在的一側才會改變，往上算「進」，往下算「出」。真值穿越次數：驗證集 95，測試集 316。

單純中線（帶寬 0，僅供診斷）。同一條線但不設遲滯帶，停在線上的蜜蜂每次晃動都會被計入：驗證集 298 次、測試集 753 次真值穿越。我們列出它只是為了說明為何需要遲滯帶或區域。

為什麼用區域規則。穿越線規則計的是軌跡「中途」發生的事件，在線附近徘徊的蜜蜂，或在線旁發生的 ID 換錯，都會多算或少算穿越；飛過巢口前方的蜜蜂也會被計入。區域規則只看軌跡相對於巢口的起點與終點，這才是「進巢」的意義。同一份追蹤輸出（本文方法、測試集）下，相對計數誤差由 83%（262 / 316，遲滯帶中線）降到 35%（119 / 341，區域）。區域規則也有弱點：它取決於軌跡的第一個與最後一個框，所以軌跡若在擁擠的巢口內斷掉，一次進出會變成兩段都不計的半截軌跡（第 13.4 節）。

提出的技術改進

觀察到的問題。框的中位數約 46 像素，蜜蜂只要一格移動超過一個框寬，前後兩框就完全不重疊；等速 Kalman 預測只有在蜜蜂維持速度時才有用，而蜜蜂往往不會。IoU 一旦為 0，ByteTrack 在任何門檻下都配不上，軌跡轉為跟丟，下一個偵測框就開出新 ID，結果拉低 IDF1 與 AssA，也讓計數出錯。使用真實偵測時問題更嚴重：漏偵測或過鬆的框讓下一次的重疊更小。

為什麼這樣改。每一項修改各自對應失敗的一個環節，而且都不需要學習參數，追蹤器仍能即時執行、也容易解釋：

  • 緩衝 IoU：如 C-BIoU [14] 所提，讓相鄰的框重新有非零、而且仍以重疊為基礎的相似度。用放大後框的 IoU 而非中心距離，代價本身就與尺度無關，也能直接沿用 ByteTrack 的門檻。
  • 自適應邊界：固定的大邊界在擁擠的蜂巢口會把相鄰的慢速蜜蜂也配在一起。只讓快速軌跡與跟丟中的軌跡放大邊界，就是把額外的搜尋範圍用在位置不確定性真正較高的地方，這也和 Kalman 共變異數的意義一致。
  • 速度衰減：跟丟的蜜蜂通常是停下、降落或轉了方向；若沿用最後的速度外推許多格，預測位置會離它重新出現的地方很遠。
  • 提高速度 process noise：相對於身體大小，蜜蜂的加速度比行人大得多，濾波器應該更相信最新的量測。
  • 延長保留時間：被其他蜜蜂擋住一到兩秒的蜜蜂可以保留原本的 ID。
  • 開新軌跡門檻 0.5：蜂群中的低分框會開出許多虛假的短軌跡，要求高信心的框才能開新軌跡可減少這種情形。由於這只是門檻變更，ByteTrack-tuned 也使用相同數值。

與提案的差異。提案原本寫的是「對正在轉彎的軌跡提高 process noise」。實作時，每條軌跡的自適應改由邊界大小（速度項與跟丟時間項）負責，process noise 則改用一個較高的固定權重；這樣 Kalman filter 本身不必修改，每個元件也都能單獨開關。提案也提到依大小正規化的中心距離，最後改用放大框的緩衝 IoU，因為它本身就已經對尺度正規化。最後，提案以穿越線計數；我們發現穿越線計數被徘徊的蜜蜂主導後，改用巢口區域規則（第 6.6 節）。

成功標準（提案時已訂定）：在同一份測試集、相同偵測結果下，HOTA 與 IDF1 高於 ByteTrack，且 ID 換錯更少。每個元件都在驗證集上做消融：其餘不變，只把該元件改回 ByteTrack 的值（表 10）。

實驗設定

公平性原則

  • Baseline 與改進方法都在同一份保留測試集上評估；測試標籤從不用於調參、挑選 checkpoint 或選擇追蹤設定。本報告的每個測試數字，都來自在驗證資料上凍結的設定、只跑一次的結果。
  • 每個實驗只改變一個主要因素。實驗一只改追蹤器（偵測快取完全相同）；實驗二只改偵測器輸入大小（追蹤器與訓練預算相同）。

失敗分析

我們以 failures.py 檢查 false positive 最多的影格，以及巢口區域內的 ID 換錯；它會把真值框（綠色）與依 ID 上色的預測框疊在一起（圖 7）。觀察到的失敗模式如下：

  • 標註差異被算成 false positive（圖 7a）。在 BEE24-34 第 391 格，23 個真值框對上 21 個未配對的預測。這些「false positive」有許多其實是真的蜜蜂，只是真值框比我們的框鬆很多，IoU 低於 0.5；其餘則是畫面邊緣花叢與地面上未被標註的蜜蜂。光是 BEE24-34 就佔了本方法 60.8 k 個測試 false positive 中的約 51 k，這解釋了它偏低的 MOTA，也說明了為何變暗（偵測到的這類蜜蜂變少）反而提高 MOTA。
  • 巢口蜂群內的 ID 換錯（圖 7b）。在 BEE24-36 第 6 到 13 格，巢口內互相接觸的蜜蜂彼此遮擋，一條軌跡跟丟後以新 ID 重新開始。區域規則因此看到兩段半截軌跡，兩段都不是「由外開始、在內結束」，這次進巢就被漏掉。這就是即使使用真值框仍有 29% 計數誤差的機制。
  • 蜜蜂消失在黑暗的巢門裡。真值會持續標註鑽進暗處的蜜蜂，偵測器卻在那裡跟丟，軌跡在到達區域內部之前就結束。加上前一種模式，使得計數誤差幾乎都是少算（表 9）。
  • 快速起飛與降落。位移大到連放大後的搜尋範圍都涵蓋不了，軌跡就會斷掉；在 BEE24-36 上，預測軌跡的長度中位數只有 0.64 秒，真值為 2.24 秒。
  • 縫合錯誤。跨越短空缺連接軌跡能減少 ID 換錯，但有時會在蜂群中把兩隻不同的蜜蜂接在一起，造成假的進出或抵銷真的進出，這是縫合讓區域計數變差的原因。

應用與展示

可實際使用的程式是 beetrack.demo。它接受影片檔或影格資料夾，逐格執行微調後的偵測器與選定的追蹤器，輸出標註後的 MP4 影片，以及所有軌跡的 CSV 檔（frame、ID、框、分數）。畫面上會顯示：每隻蜜蜂的框與 ID（顏色由 ID 決定）、表示行進方向的一秒尾跡；巢口區域（或計數線）；以及一行狀態列，列出即時進出次數、目前追蹤中的蜜蜂數、追蹤器名稱與處理 FPS（以偵測加追蹤時間、30 格移動視窗計算）。加上 --zone 時，demo 使用與評估完全相同的區域規則：軌跡消失超過 track buffer 後才計入，所以計數會在蜜蜂進出後約 2.4 秒出現。不加時，demo 計算穿越一條線的次數，線的高度可由命令列設定。追蹤器（本文或 ByteTrack）也是命令列選項，同一段影片可以用兩種追蹤器分別展示。

典型用法：uv run python -m beetrack.demo --source data/BEE24/test/BEE24-36/img1 --tracker ours --zone BEE24-36。執行環境由 uv.lock 鎖定，每位組員都能以 uv sync 重現。

未見過影片的展示。我們沒有自行拍攝影片，也沒有使用 BEE24 以外的蜂巢影片。因此展示使用 BEE24-36：這是 5,000 格（200 秒）的官方測試序列，從未用於訓練、checkpoint 挑選或追蹤器調參，在這個意義上是「未見過」的影片；但它來自同一個資料集，不能當作推廣到其他地點或攝影機的證據。在這段影片上，demo 平均 66 FPS（偵測＋追蹤，640 px，不含解碼），計數為進 40／出 22，真值為 49 / 32，與離線分析完全相同。輸出影片為 runs/demo/BEE24-36_ours.mp4；圖 8 是其中一格。

限制與未來工作

  • 單一資料集與地點。所有結果（包括 demo）都來自 BEE24。其他地點的攝影機、蜂箱種類與光線可能不同，需要一小段新地點的標註影片才能確認推廣能力。
  • 計數受限於軌跡斷裂。即使用真值框，區域誤差仍有 29%。更大的偵測器、縫合或短軌跡過濾都沒有解決這個問題；需要能在蜜蜂接觸時、以及穿過黑暗巢門時維持 ID 的方法。
  • 計數規則。計數由真值軌跡推得，並非真實進巢的標註；區域多邊形也是每台攝影機手繪一次。只標註到巢門口的蜜蜂，與被一路標進暗處的蜜蜂，可能會被計得不同。這套規則適合比較追蹤器，不適合產生絕對的蜂群統計。
  • 相對調整後 baseline 的提升有限。與使用相同開新軌跡門檻的 ByteTrack 相比，本方法 HOTA 打平、IDF1 略低；優勢在 MOTA、ID 換錯、掉幀穩健性與區域計數。
  • 人工穩健性測試。變暗、過曝、模糊與雜訊都是簡單的全域影像變化；真實的黃昏、雨天或樹葉晃動的陰影會隨空間變化，且在時間上相關。
  • 人工設計的運動模型。邊界與雜訊參數是在六段驗證片段上調出來的；學習式運動模型，或 OC-SORT [10] 那樣以觀測值回頭修正，可能更能適應每隻蜜蜂的飛行。
  • 硬體。速度只在一台筆電 GPU 上量測；沒有嘗試邊緣裝置部署（例如在蜂箱旁的 Jetson 上使用 ONNX 或 TensorRT）。

未來工作：能在蜜蜂接觸時仍維持 ID 的關聯方法（例如短期外觀或姿態特徵，或偵測與追蹤聯合學習）；把黑暗巢門明確建模為「已進巢」狀態；真實進巢事件的計數標註；自行拍攝蜂巢影片；以及量化後的邊緣推論。

結論

BeeTrack 是一套完整、可重現的系統，能把蜂巢口影片轉成蜜蜂 ID、軌跡與進出計數。在相同偵測下，運動自適應關聯相對預設 ByteTrack 把測試 HOTA 由 40.2 提升到 45.2、IDF1 由 48.1 提升到 55.7，ID 換錯由 2,186 次降到 1,314 次；與使用相同開新軌跡門檻的 ByteTrack 相比，HOTA 打平（45.2），MOTA、ID 換錯與計數較佳。計數上最大的改善來自規則本身：以巢口區域取代畫面中線，使本方法的相對計數誤差由 83% 降到 35%。Oracle 實驗顯示即使框完全正確仍有 29%，剩下的誤差來自擁擠巢口的軌跡斷裂。軌跡縫合有助於穿越線計數，卻傷害區域計數與 HOTA；1280 px 偵測器提升了 HOTA（48.0）與 MOTA（60.3），但沒有改善計數。本方法在掉幀處理下退化最緩和，並在所有人工劣化下維持最佳的區域計數。系統在筆電 GPU 上離線約 54 FPS、即時 demo 66 FPS。所有調參只使用驗證資料，測試集每個設定只跑一次。
