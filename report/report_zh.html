摘要

蜂巢出入口的流量，也就是出巢與回巢的蜜蜂數量，能直接反映蜂群的活動力，但靠人眼計數無法長期進行。本文提出 BeeTrack：一套從蜂巢口影片中偵測每一隻蜜蜂、為每隻蜜蜂維持固定 ID、繪出軌跡，並計算穿越虛擬計數線之進出數量的系統。偵測器採用 COCO 預訓練的 YOLO11-s，以 BEE24 資料集微調；追蹤器以 ByteTrack 為基礎。蜜蜂體型小、外觀幾乎相同且飛行快速，我們以 oracle 實驗證明：即使偵測完全正確，預設的 ByteTrack 在驗證集上也只有 HOTA 71.3，關聯本身就是瓶頸。我們提出的改進「運動自適應關聯」以緩衝 IoU 取代一般 IoU，且搜尋範圍會隨軌跡速度與跟丟的影格數放大；同時讓跟丟軌跡的速度逐格衰減、提高 Kalman filter 的速度 process noise，並延長跟丟軌跡的保留時間。所有參數只在驗證資料上調整，BEE24 官方的 5 支測試影片（10,762 格、168,230 個框）只用於最終評估。在相同偵測結果下，測試集 HOTA 由 TODO 變為 TODO，IDF1 由 TODO 變為 TODO，ID 換錯次數由 TODO 變為 TODO；在 753 次真值穿越中，計數誤差由 TODO 降至 TODO。第二組對照實驗比較偵測器輸入 640 與 1280 像素；穩健性分析涵蓋人工變暗、過曝、動態模糊與感測器雜訊、跳格處理，以及不同擁擠程度。整套系統在 RTX 4060 筆電 GPU 上的處理速度為 TODO FPS。

關鍵詞：多目標追蹤、蜜蜂監測、YOLO11、ByteTrack、緩衝 IoU、Kalman filter、HOTA、穿越線計數

緒論與問題定義

研究動機

養蜂人與授粉研究者之所以觀察蜂巢出入口，是因為外出採集的流量會很快反映天氣、蜜源、農藥與疾病的變化。在出入口架一台攝影機並不貴，難的是把影片轉成數字：短短幾分鐘的影片就包含上千次飛行，人工計數既慢又容易出錯。若能自動追蹤每一隻蜜蜂並計算進出數量，就能做到連續且客觀的監測。

問題的困難之處

多數多目標追蹤器是為行人設計的，蜜蜂比行人難追得多。在 950 × 600 的畫面中，一個蜜蜂框大約只有 46 × 50 像素；數十隻蜜蜂外觀幾乎無法區分，外觀特徵的幫助有限；而且蜜蜂會在幾格之內加速、轉向或降落。以等速 Kalman filter 預測位置、再用框的重疊來配對的追蹤器，常會遇到快速蜜蜂的預測框與下一格偵測框完全不重疊的情形，於是軌跡跟丟、以新的 ID 重新開始，甚至和旁邊的蜜蜂對調 ID。偏偏蜂巢口正是最擁擠、也正是要計數的區域。

目標、輸入與輸出

本系統對應課程的 Project 1（即時多目標偵測與追蹤）。輸入為蜂巢口影片（影片檔或影格資料夾）；輸出為每一格中每隻蜜蜂的框與追蹤 ID、每個 ID 的軌跡與方向、水平計數線上的累計進出數量、實測處理速度、標註後的影片，以及所有軌跡的 CSV 檔。具體目標如下：

  1. 微調一個能偵測蜜蜂的深度學習偵測器（R1）；
  2. 建立線上追蹤器，在漏偵測與短暫遮擋下仍能維持 ID，並提供軌跡與計數分析（R2）；
  3. 提出有理由的關聯改進，在相同偵測結果下與預設 ByteTrack 比較（R3）；
  4. 完成兩組對照實驗：關聯方法與偵測器輸入大小（R4），以 HOTA、IDF1、MOTA、ID 換錯、計數誤差與 FPS 量化評估，並分析至少三種困難條件（R5）；
  5. 提供可重現、能端到端處理影片的 demo 程式（R6）。

本文貢獻

  • 為 BEE24 建立無資料洩漏的評估流程：驗證集包含長時間的擁擠片段，並修正官方標註中重複 ID 的問題，產生 TrackEval 可用的真值。
  • 提出運動自適應關聯：在 ByteTrack 內部做少量修改，每一項都能單獨關閉做消融實驗，專門處理小而快速物體的失敗模式。
  • 以 oracle 分析區分關聯錯誤與偵測錯誤，並在影像劣化、跳格與擁擠程度三類條件下做穩健性研究。
  • 訂定明確的穿越線計數規則，真值與預測套用同一規則；demo 可輸出含即時計數與 FPS 的標註影片。

相關研究

物件偵測。YOLO 系列 [1] 屬於單階段偵測器，一次前向傳遞即可密集預測所有框，是即時 tracking-by-detection 最常見的選擇。我們使用 Ultralytics 目前的版本 YOLO11 [2] 的 small 規模。RT-DETR [3] 等 Transformer 偵測器速度相近，但所需記憶體與訓練時間超出我們 8 GB 筆電 GPU 能從容負擔的範圍。

Tracking-by-detection。SORT [4] 以等速 Kalman filter [5] 預測位置，再以 IoU 為代價、用匈牙利演算法 [6] 配對。DeepSORT [7] 加入外觀重識別特徵，但目標外觀都相同時幫助不大。ByteTrack [8] 保留低信心分數的偵測框並在第二階段配對，能找回被部分遮擋的目標；它是 Ultralytics 的預設追蹤器，也是本專題的 baseline。BoT-SORT [9] 加入相機運動補償與外觀特徵，但 BEE24 的相機固定不動，兩者都派不上用場。OC-SORT [10] 在軌跡重新被觀測到時，以觀測值修正跟丟期間的 Kalman 狀態，以處理非線性運動造成的漂移。

不規則運動。DanceTrack [11] 指出：在 MOT17 [12]、MOT20 [13] 上調好的追蹤器，遇到外觀一致、運動多變的目標時表現會明顯下降，這正是蜜蜂的情況。C-BIoU [14] 在計算 IoU 前同時放大軌跡框與偵測框，讓框不重疊的快速物體仍能配對，並串接兩種緩衝大小。我們沿用緩衝 IoU 的想法，但讓緩衝大小依每條軌跡的狀態（速度與跟丟時間）決定，而不是固定的串接層級。

昆蟲追蹤。Bozek 等人 [15] 以分割網路加上時間連結，追蹤蜂巢內部密集的蜜蜂。BEE24 [16] 隨 TOPICTrack 一同發表，該方法平行進行運動與外觀關聯，作者在 BEE24 測試集上報告 HOTA 46.6、IDF1 59.7、MOTA 66.7。這些數字使用不同的偵測器與訓練流程，本文僅作為背景參考，並非對照比較。

評估指標。CLEAR MOT 指標 [17]（MOTA、ID 換錯）主要受偵測品質影響；IDF1 [18] 衡量 ID 的一致性；HOTA [19] 則同時平衡偵測（DetA）與關聯（AssA）準確度。所有指標皆以官方實作 TrackEval [20] 計算。人工影像劣化的設計參考 Hendrycks 與 Dietterich 的 common corruption 基準 [21]。

資料集與前處理

來源與標註

BEE24 [16] 共 36 支蜂巢口影片，25 fps，解析度約 950 × 600（其中一段為 810 × 430），共有 446,908 個標註框、4,559 個蜜蜂 ID，平均每格 19.0 隻（最多 52 隻）。每個框都附有 MOTChallenge 格式的追蹤 ID（frame、id、x、y、w、h），符合規範第 7B 節「追蹤指標必須有 ID 標註」的要求。資料可公開下載（2.3 GB），不需註冊；資料集頁面沒有寫明授權，因此我們只用於本課程並引用論文。影片中只有昆蟲，沒有拍到任何人。

資料切分與防止洩漏

官方切分為 31 支訓練影片與 5 支測試影片。測試集（BEE24-12、-13、-16、-34、-36；10,762 格、168,230 個框）完全不用於訓練、模型挑選或參數調整，每個最終設定只評估一次。驗證集則從訓練影片中切出，用於偵測器的 early stopping 與所有追蹤器調參（表 1）。

提案時原本規劃以「整段訓練序列」作為驗證集。實作時發現，短的訓練序列（75 到 258 格）每格蜜蜂數遠少於兩支長測試影片；後者各有 5,000 格，且包含最擁擠的片段。若驗證集沒有長而擁擠的片段，追蹤器就會被調到錯誤的情境。因此我們保留四段完整的短序列（BEE24-10、-15、-24、-28），另外再取兩支長訓練影片 BEE24-33 與 -35 的最後 1,000 格。這兩段尾端與訓練影格之間隔著 50 格不屬於任何一方的間隔，避免幾乎相同的相鄰影格跨界洩漏。prep.py 會以 assert 檢查沒有任何一格同時屬於兩個切分。

前處理

  • 偵測器標籤：每個框先裁切到影像範圍內，寬或高不足 1 像素者捨棄，再寫成單一類別的 YOLO 標籤（0 cx cy w h，正規化座標）。沒有蜜蜂的影格會產生空白標籤檔，作為負樣本。
  • 取樣間隔：25 fps 影片的相鄰影格幾乎相同。長影片（≥ 1,000 格）每 5 格取 1 格作為訓練影像（驗證與測試影像每 10 格取 1 格，僅用來算 mAP）；短影片每格都用。最後得到訓練 3,740 張、驗證 840 張、測試 1,762 張偵測器影像。
  • 評估用真值：每段驗證與測試序列都寫成 TrackEval 讀取的 MOTChallenge 資料夾：gt.txt（confidence、class、visibility 皆設為 1）與 seqinfo.ini。驗證集尾段的影格編號重新從 1 開始。
  • 標註修正：BEE24-14、-15、-33、-35（皆為官方訓練影片）共有 993 列在同一格中把同一個 ID 給了兩隻蜜蜂，TrackEval 不接受這種檔案。評估真值中，多出來的那一筆保留原本的框、改給一個新的 ID；這只影響驗證序列，測試序列沒有這種情形。
  • 跳格真值：穩健性實驗所需的測試真值，另外以每 k 格取 1 格（k = 2、3、5）並重新連續編號寫出，規則與追蹤器輸入完全相同。

資料流。prep.py 把原始標註轉成 YOLO 標籤、影像清單與 TrackEval 真值；train.py 微調偵測器；detect.py 對每一格驗證或測試影像只跑一次偵測器（可先加上人工劣化），把框（frame, x1, y1, x2, y2, score）存成 NumPy 快取；track.py 逐格把快取的框餵給任一追蹤器，輸出 MOTChallenge 格式的結果；evaluate.py 以 TrackEval 計算 HOTA、CLEAR、Identity 指標與穿越線計數誤差；sweep.py 在驗證資料上一次跑完整組追蹤設定；analytics.py 產生軌跡、熱度圖、計數與軌跡長度圖；demo.py 走線上路徑，輸出標註影片與 CSV。

為什麼要快取偵測結果。實驗一只能改變追蹤器。偵測器只跑一次、再把一模一樣的框重播給每一種追蹤設定，就能排除偵測端每次執行的差異（FP16 的非決定性、前處理），讓比較完全受控；而且數十種設定的掃描在 CPU 上幾分鐘就能跑完。

方法與演算法

偵測器

YOLO11-s 是 anchor-free 的單階段偵測器，由 CSP 式骨幹、特徵金字塔頸部，以及在三個 stride（8、16、32）上分別預測類別分數與框分佈的 decoupled head 組成。輸入 640 像素時，約 46 像素的蜜蜂在 stride 8 上大約只佔 6 格，最細的偵測頭還夠用，但對較小的蜜蜂餘裕不多；輸入加倍為 1280 像素可讓解析度加倍，但計算量變成四倍，這正是實驗二要量測的取捨。偵測結果保留到信心分數 0.05，因為 ByteTrack 的第二階段刻意使用低分框。

Baseline 追蹤器：ByteTrack

每條軌跡的 Kalman 狀態為 x = (cx, cy, a, h, ċx, ċy, ȧ, ḣ)（中心、長寬比、高度及其速度），採等速狀態轉移。process noise 與量測雜訊都和框高 h 成正比，速度的標準差為 σv = wv·h，預設 wv = 1/160。每一格的處理步驟：

  1. 所有軌跡（追蹤中與跟丟中）先預測下一格的位置。
  2. 分數 ≥ 0.25 的偵測框與軌跡配對，代價為 C = 1 − IoU·s（IoU 與偵測分數 s 融合），以匈牙利演算法求解，代價 > 0.8 的配對不採用。
  3. 剩下的追蹤中軌跡再與低分框（0.1 ≤ s < 0.25）以一般 IoU 配對，代價 > 0.5 者不採用。
  4. 尚未確認的新軌跡與剩下的高分框配對；仍未配對、且 s ≥ 0.25 的偵測框開新軌跡。
  5. 超過 track_buffer = 30 格（1.2 秒）沒有配對的軌跡被移除；在此之前屬於「跟丟」狀態，仍可重新啟用。

本文改進：運動自適應關聯

我們要解決的是幾何上的失敗：快速蜜蜂的預測框與下一格的偵測框沒有重疊，IoU 為 0，任何門檻都配不上。我們在 ByteTrack 內部做了四項修改；設計理由與逐項消融見第 9 章。

(a) 自適應緩衝 IoU。計算 IoU 之前，寬 w、高 h 的框 (x1, y1, x2, y2) 四邊各放大比例 r：

Br = (x1 − rw,  y1 − rh,  x2 + rw,  y2 + rh)
(1)

偵測框使用固定的基本緩衝 b；軌跡 i 的緩衝則隨距上次配對的影格數 ℓi，以及以「框高／格」為單位的速度而增加：

ri = b + g · min(ℓi, 10) + k · min(‖(ċx, ċy)‖hi, 1)
(2)
Cij = 1 − IoU(Bri(tracki), Bb(detj)) · sj
(3)

此代價取代第一階段（高分框）與未確認軌跡配對中的一般 IoU；第二階段（低分框）仍維持一般 IoU，只有真的重疊時才接受弱偵測。因此靜止且剛配對上的蜜蜂只用小緩衝，而快速移動或已經消失好幾格的蜜蜂，則在較大的範圍內搜尋。

(b) 跟丟軌跡的速度衰減。軌跡處於跟丟狀態時，每次預測前把速度乘上 δ（v ← δ·v），避免看不見的蜜蜂沿著過時的速度一路飄走；搜尋範圍改由式 (2) 擴大。

(c) 提高速度 process noise。把速度權重 wv 從 1/160 提高為 qv，讓濾波器更快跟上突然的加速與轉向。

(d) 延長跟丟軌跡保留時間。track_buffer 從 30 格延長為 60 格（2.4 秒），讓短暫躲在其他蜜蜂後方或短暫降落的蜜蜂能以原 ID 重新啟用。

計數規則

BEE24 沒有計數標註，因此我們由軌跡定義計數，並對真值與預測軌跡套用同一條規則。在畫面高度一半處放一條水平線 y = H/2；對每條軌跡依時間順序取 cy − H/2 的正負號，剛好落在線上的影格忽略不計，每次正負號改變就算一次穿越：往上（y 變小）算「進」，往下算「出」。追蹤器在序列集合 S 上的計數誤差定義為

E = Σs∈S ( |Îs − Is| + |Ôs − Os| )
(4)

其中 I、O 是真值的進、出次數，Î、Ô 是預測值。E 會與真值穿越總數一起報告（測試集共 753 次）。這條規則刻意保持簡單：在線上發生 ID 換錯，或軌跡跟丟後在另一側重新開始，都可能少算或多算一次，所以計數誤差對我們想消除的關聯錯誤特別敏感。把線放在畫面中間是為了讓各序列可以互相比較的評估約定；demo 中使用者可以把線放在任何高度。

提出的技術改進

觀察到的問題。Oracle 實驗顯示，即使框完全正確，關聯仍會失敗。框的中位數約 46 像素，蜜蜂只要一格移動超過一個框寬，前後兩框就完全不重疊；等速 Kalman 預測只有在蜜蜂維持速度時才有用，而蜜蜂往往不會。IoU 一旦為 0，ByteTrack 在任何門檻下都配不上，軌跡轉為跟丟，下一個偵測框就開出新 ID，結果拉低 IDF1 與 AssA，也讓穿越計數出錯。

為什麼這樣改。每一項修改各自對應失敗的一個環節，而且都不需要學習參數，追蹤器仍能即時執行、也容易解釋：

  • 緩衝 IoU：如 C-BIoU [14] 所提，讓相鄰的框重新有非零、而且仍以重疊為基礎的相似度。用放大後框的 IoU 而非中心距離，代價本身就與尺度無關，也能直接沿用 ByteTrack 的門檻。
  • 自適應緩衝：固定的大緩衝在擁擠的蜂巢口會把相鄰的慢速蜜蜂也配在一起。只讓快速軌跡與跟丟中的軌跡放大緩衝，就是把額外的搜尋範圍用在位置不確定性真正較高的地方，這也和 Kalman 共變異數的意義一致。
  • 速度衰減：跟丟的蜜蜂通常是停下、降落或轉了方向；若沿用最後的速度外推 60 格，預測位置會離它重新出現的地方很遠。
  • 提高速度 process noise：相對於身體大小，蜜蜂的加速度比行人大得多，濾波器應該更相信最新的量測。
  • 延長保留時間：被其他蜜蜂擋住一到兩秒的蜜蜂可以保留原本的 ID。

與提案的差異。提案原本寫的是「對正在轉彎的軌跡提高 process noise」。實作時，每條軌跡的自適應改由緩衝大小（速度項與跟丟時間項）負責，process noise 則改用一個較高的固定權重；這樣 Kalman filter 本身不必修改，每個元件也都能單獨開關。提案也提到依大小正規化的中心距離，最後改用放大框的緩衝 IoU，因為它本身就已經對尺度正規化。

成功標準（提案時已訂定）：在同一份測試集、相同偵測結果下，HOTA 與 IDF1 高於 ByteTrack，且 ID 換錯更少。每個元件都在驗證集上做消融：其餘不變，只把該元件改回 ByteTrack 的值（表 10）。

實驗設定

公平性原則

  • Baseline 與改進方法都在同一份保留測試集上評估；測試標籤從不用於調參、挑選 checkpoint 或選擇追蹤設定。
  • 每個實驗只改變一個主要因素。實驗一只改追蹤器（偵測快取完全相同）；實驗二只改偵測器輸入大小（追蹤器與訓練預算相同）。
  • 硬體、seed（0）、前處理、模型版本、訓練預算與評估設定皆固定，列於表 4；每個實驗都寫出目的、控制條件、結果、解讀與失敗案例。

偵測：precision、recall、mAP@0.5、mAP@0.5:0.95。追蹤：HOTA 及其偵測、關聯分量，IDF1、MOTA、ID 換錯次數（IDSW）、false positive 與 false negative。門檻 α 下的 HOTA 是偵測準確度與關聯準確度的幾何平均，再對 α 取平均：

可運作的應用程式是 beetrack.demo。它接受影片檔或影格資料夾，逐格執行微調後的偵測器與選定的追蹤器，輸出標註過的 MP4 影片與包含所有軌跡（frame、ID、框、分數）的 CSV 檔。畫面上會顯示每隻蜜蜂的框與 ID（顏色由 ID 決定）、代表行進方向的一秒尾跡、計數線，以及一行狀態列：即時進出數量、目前追蹤中的蜜蜂數、追蹤器名稱，和以最近 30 格滑動平均量測的處理 FPS（偵測＋追蹤）。計數線高度與追蹤器（本文方法或 ByteTrack）都是命令列參數，因此可以把同一段影片用兩種追蹤器並排展示。

典型用法：uv run python -m beetrack.demo --source data/BEE24/test/BEE24-36/img1 --tracker ours。執行環境由 uv.lock 鎖定，每位組員只要 uv sync 就能重現。Demo 也在開發過程中完全沒用過的輸入上執行過：TODO（例如一段新的蜂巢影片；因為沒有真值，僅作為質性證據並明確標示）。

限制與未來工作

  • 只有一個資料集與場地。所有結果都來自 BEE24；其他地點的相機、蜂箱形式與光線可能不同，需要新場地的少量標註影片才能確認泛化能力。
  • 穩健性測試是人工合成的。變暗、過曝、模糊與雜訊都是簡單的全域影像變化；真實的黃昏、下雨或樹葉晃動的陰影在空間上不均勻，而且隨時間相關。
  • 計數規則。計數是由真值軌跡在畫面中線上定義的，並非實際進入蜂巢的標註；穿越計數線但沒有進巢的蜜蜂仍會被算進去。這套規則適合比較追蹤器，不適合當作蜂群的絕對統計。
  • 人工設計的運動模型。緩衝與雜訊參數只在六段驗證片段上調整；學習式運動模型，或像 OC-SORT [10] 那樣以觀測值回頭修正狀態，可能更能適應每隻蜜蜂的飛行方式。
  • 沒有使用外觀特徵。蜜蜂雖然長得很像，但姿態與攜帶花粉等細微差異，或許仍有助於遮擋後的短期重識別。
  • 硬體。速度只在一張筆電 GPU 上量測，沒有嘗試在蜂箱旁的邊緣裝置（例如 Jetson 上的 ONNX 或 TensorRT）部署。

未來工作：針對起飛與降落的學習式或多模型（IMM）運動估計；以實際巢門為範圍的區域計數；用我們自己的攝影機做長時間部署；以及量化後的邊緣推論。

結論

BeeTrack 是一套完整且可重現的系統，能把蜂巢口影片轉換成蜜蜂 ID、軌跡與進出數量。Oracle 實驗顯示，限制小而快速之蜜蜂追蹤效果的不只是偵測，關聯本身也是瓶頸。運動自適應關聯以放大框配對，放大幅度依每條軌跡的速度與跟丟時間調整，並修正跟丟軌跡的運動模型；在相同偵測結果下，相較於 ByteTrack，測試集 HOTA 變化 TODO、IDF1 變化 TODO、ID 換錯變化 TODO，計數誤差由 TODO 降至 TODO。實驗二顯示 1280 px 輸入 TODO。系統在筆電 GPU 上可達 TODO FPS。所有調參都只用驗證資料，每個最終設定只在測試集上評估一次。

外部模型、資料集與 AI 使用揭露

  • 預訓練模型：Ultralytics YOLO11-s 的 COCO 權重（yolo11s.pt），AGPL-3.0。我們以 BEE24 微調，未使用其他預訓練權重。Baseline 追蹤器為 Ultralytics 的 ByteTrack 實作，本文追蹤器繼承自它。
